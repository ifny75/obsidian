# Obsidian — архитектура

Приватный мессенджер с закрытым доступом. Self-hosted на домашнем сервере за Cloudflare Tunnel.

Документ — контракт между слоями. Клиент и сервер пишутся по нему, а не по внутренним договорённостям.

---

## 1. Принципы

1. **Сервер не доверенный.** Он видит только шифротекст. Компрометация сервера не раскрывает переписку.
2. **Ключи не покидают устройство.** Никогда, ни в каком виде, ни в бэкапе, ни в логах.
3. **Метаданных минимум.** Чего нет в БД — то не изымут и не утечёт.
4. **Не изобретать криптографию.** Только MLS (RFC 9420), Ed25519, XChaCha20-Poly1305, Argon2id.
5. **Fail closed.** Ошибка проверки подписи, неизвестный опкод, битый кадр — разрыв соединения, а не «попробуем разобрать».

---

## 2. Модель угроз

### Защищаем от

| Противник | Механизм защиты |
|---|---|
| Провайдер, сканеры, случайный трафик | TLS, закрытый вход через Cloudflare Access |
| Компрометация сервера, изъятие диска | E2EE — на сервере нет ключей; шифротексты удаляются после доставки |
| Компрометация клиентской БД (украден ноут) | Запечатанные записи, ключ из Argon2id(пароль) + системный keystore |
| Cloudflare как наблюдатель контента | Всё содержимое зашифровано до попадания в туннель |
| Компрометация ключа в прошлом | MLS: forward secrecy + post-compromise security |
| Сервер подменяет ключи (MITM) | Ручная верификация отпечатков контактов (safety numbers) |

### НЕ защищаем (осознанно)

- **Метаданные уровня сети.** Cloudflare видит IP, тайминги, размеры. Против этого — только onion-транспорт (фаза 7).
- **Факт связи на сервере.** Сервер знает, какому устройству доставить конверт. Полный sealed sender — фаза 6.
- **Скомпрометированное устройство.** Кейлоггер или root на телефоне ломает всё. Вне модели.
- **Принуждение пользователя.** Deniability и панические пароли — не в scope v1.

## 3. Компоненты

```
┌──────────────────┐        ┌──────────────────┐
│ Windows client   │        │ Android client   │
│ Tauri v2         │        │ Java UI          │
│ WebView2 (UI)    │        │ JNI              │
└────────┬─────────┘        └────────┬─────────┘
         │ прямой линк                │ 5 C-функций
    ┌────┴────────────────────────────┴────┐
    │        obsidian-core (Rust)          │
    │  MLS · ключи · хранилище · сеть      │
    └──────────────────┬───────────────────┘
                       │ WSS (бинарные кадры) + HTTPS
              ┌────────┴────────┐
              │   Cloudflare    │  ← видит IP/тайминги, не видит контент
              │  Access+Tunnel  │
              └────────┬────────┘
              ┌────────┴────────┐
              │ obsidian-server │  Node 24 + TS
              │   тупой релей   │
              └────────┬────────┘
                  ┌────┴────┐
                  │ SQLite  │  шифротексты с TTL
                  │ blobs/  │  вложения (шифр. на клиенте)
                  └─────────┘
```

**Граница доверия проходит по obsidian-core.** Всё выше него — UI, ему можно отдавать plaintext. Всё ниже — враждебная среда.

### Граница FFI

`obs_init` · `obs_send` · `obs_poll` · `obs_free` · `obs_shutdown` — и всё. Наружу ходят команды и события в JSON (`command.rs`), а не вызовы на каждую операцию: богатый API пришлось бы биндить дважды, для JNI и для Tauri.

События **забираются опросом**, а не колбэком. Колбэк из чужого потока в JVM требует `AttachCurrentThread` и `GlobalRef` и легко даёт UB при ошибке; блокирующий `obs_poll` из одного фонового Java-потока не требует ничего.

## 4. Идентичность и ключи

Ни телефонов, ни email, ни паролей на сервере.

| Ключ | Алгоритм | Где живёт | Назначение |
|---|---|---|---|
| Identity key | Ed25519 | Только на устройствах пользователя | Корень личности, подписывает устройства |
| Device key | Ed25519 | На конкретном устройстве | Аутентификация сессии |
| MLS KeyPackage | X25519 + Ed25519 | Публичная часть на сервере | Асинхронное добавление в группу |
| DB key | 32 байта | Производный, в памяти | Запечатывание локальных записей |

**Адрес пользователя = hex его identity pubkey.** `handle` — необязательный алиас для UX; его отсутствие не мешает работе. Каждый handle на сервере — это лишние метаданные, поэтому он opt-in.

**Мультидевайс.** Identity key подписывает device key — получается сертификат устройства:

```
device_cert = Ed25519_sign(identity_priv, "obsidian-device-v1" || identity_pub || device_pub)
```

Сервер проверяет цепочку при регистрации устройства и отдаёт её другим клиентам. Клиент-отправитель обязан проверить сертификат сам — сервер здесь не авторитет, а кэш.

**Шифрование всегда per-device.** Отправитель получает список устройств получателя и шифрует N раз. Сервер никогда не размножает конверты сам — он не умеет.

## 5. Криптография

- **Групповое и парное шифрование — MLS (RFC 9420), OpenMLS.** Диалог 1:1 — это группа из двух участников, отдельного кода нет. Даёт forward secrecy и post-compromise security в обоих случаях.
- **Ciphersuite** — MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519.
- **Локальная БД клиента — обычный SQLite с запечатанными записями**, не SQLCipher. Каждая запись шифруется XChaCha20-Poly1305, AAD привязывает её к своему месту в базе. Причина замены: SQLCipher под MSVC требует сборки OpenSSL (nasm + windows-perl), а под Android NDK — отдельной возни; собираться должно везде одинаково. Побочный эффект оказался полезным: у SQLCipher незашифрованным остаётся заголовок файла, здесь же в открытом виде лежат только соль, идентификаторы, метка беседы и время.
- **Ключ БД — Argon2id** (m=64 MiB, t=3, p=4) от пароля, соль в открытом заголовке. Где есть системный keystore (Android Keystore, Windows DPAPI) — ключ дополнительно оборачивается в него.
- **Вложения — XChaCha20-Poly1305**, случайный ключ на файл, ключ уходит внутри MLS-сообщения.

**MLS-лист привязан к устройству.** У MLS своя пара подписи, и сама по себе она не связана с ключом
устройства ничем. Поэтому в BasicCredential кладётся не идентификатор, а привязка:

```
mls_credential = device_pub || Ed25519_sign(device_priv, "obsidian-mls-v1" || mls_signature_pub)
```

Она проверяется в трёх местах: при разборе чужого KeyPackage (сервер мог подсунуть чужой), при вступлении
в группу по Welcome (кто именно позвал) и **на каждом входящем сообщении** (состав группы меняется, и новый
лист тоже обязан доказать, что за ним стоит настоящее устройство). Без этой привязки «участник группы» и
«владелец устройства» — разные сущности, и сервер может подставить в группу кого угодно.

Доменные префиксы подписей: `obsidian-auth-v1`, `obsidian-device-v1`, `obsidian-mls-v1`.

**Проверка подписей — строго по RFC 8032.** Режим ZIP-215, включённый по умолчанию и в noble, и в `ed25519-dalek::verify`, принимает точки малого порядка: ключ из одних нулей с подписью из одних нулей проходит проверку. Такую личность подписал бы кто угодно — вместе с привязанным к ней оплаченным счётом. Обе стороны обязаны использовать строгий режим (`zip215: false` в noble, `verify_strict` в Rust); это закреплено тестами с одинаковым списком из девяти кодировок.

**Верификация контактов обязательна в UI.** Отпечаток = SHA-256 от identity pubkey, показывается
группами цифр. Без сравнения отпечатка сервер способен на MITM — это единственная дыра, которую
криптография сама не закрывает.

Сверять есть что два раза, и это разные вещи:

| Что | Откуда | Когда меняется | Что доказывает |
|---|---|---|---|
| `safety_number` | SHA-256 от пары ключей устройств, порядок нормализован сортировкой | только при смене ключей | между вами нет третьего |
| `epoch_code` | epoch authenticator MLS (RFC 9420 §8.2) | на каждом коммите | прямо сейчас вы в одном состоянии |

Первое сверяют один раз при знакомстве, второе — когда есть сомнения. Сортировка ключей в
`safety_number` не косметика: без неё Алиса и Боб увидели бы разные числа и сверять было бы нечего.

**Сверять нужно по другому каналу.** Показать код в той же переписке — значит показать его тому, от
кого защищаемся.

## 5a. Проверки на пути отправки

Криптография может сойтись, а состояние — быть подставленным. Три проверки ловят именно это; каждая
дешёвая и стоит в горячем пути.

1. **Состав беседы.** Диалог один на один — это ровно два участника: мы и тот, кому пишем. Лишний
   лист в такой группе выглядит ровно как атака с участием сервера. Отправка в этом случае **не
   происходит**: открытый текст в подставленную группу уходить не должен.
2. **Привязка каждого участника** (§5) перепроверяется при построении состава, а не только при
   вступлении.
3. **Канарейка на открытый текст.** Тело сообщения не имеет права быть видимым в шифротексте.
   Настоящее шифрование этого никогда не допустит — проверка ловит не слабость алгоритма, а обрыв в
   проводке: пропущенный вызов, перепутанный буфер, вернувшийся отладочный путь. Короткие тела
   (меньше 8 байт) не проверяются: там случайное совпадение реально и дало бы ложную тревогу.

На приёме состав сверяется с тем собеседником, которого мы в этой беседе ждём.

Всё это приходит интерфейсу отдельным событием `anomaly`, а не общим `failed`: «не получилось» и
«похоже на атаку» пользователь должен различать.

## 5b. Восстановление доступа

Потеря устройства не должна означать потерю личности. Два способа, и они не равноценны.

### Код восстановления

Сам identity-ключ в base32 с контрольной суммой: 55 символов, 11 групп по пять.
Алфавит без `0`/`O` и `1`/`I` — их путают при переписывании от руки.

Отдельного «сида», из которого выводится ключ, нет намеренно: тогда код умели бы
получить только новые аккаунты, а уже зарегистрированным пришлось бы менять
личность. Здесь код умеет выдать кто угодно и когда угодно.

Кодировка строгая: хвостовые биты обязаны быть нулевыми. Без этой проверки
опечатка в последнем символе — он несёт всего три значащих бита — меняла бы
только набивку и проходила бы мимо контрольной суммы, молча создавая **другую**
валидную личность.

Сервер об этом способе не знает ничего и не участвует в нём.

### Логин и пароль

Запечатанная копия identity-ключа на сервере. Открыть её умеет только пароль, а
пароль с устройства не уходит.

```
salt     = SHA256("obsidian-recovery-salt-v1" || login)
kdf(64)  = Argon2id(password, salt, m=128 MiB, t=3, p=4)
token    = kdf[0..32]          → уходит на сервер как доказательство
seal     = kdf[32..64]         → не уходит никогда
loginId  = SHA256("obsidian-recovery-login-v1" || login)
verifier = SHA256("obsidian-recovery-verifier-v1" || token)
sealed   = XChaCha20-Poly1305(seal, identityPriv, aad = domain || loginId)
```

Сервер хранит `(loginId, identity, verifier, sealed)` и сравнивает
`SHA256(domain || token)` со своим `verifier` в постоянное время.

**Зачем доказательство отдельно от ключа.** Логин угадывается — люди берут своё
имя. Без `token` кто угодно скачал бы посылку и перебирал пароль офлайн, на
своём железе. С ним каждая попытка стоит одного прогона Argon2id **и** одного
запроса к серверу, где стоит ограничитель частоты: 10 в час на IP и отдельно 10
в час на логин.

**Соль детерминированная**, выведена из логина: при восстановлении на чистом
устройстве взять случайную соль неоткуда, а спрашивать её у сервера до проверки
пароля значило бы отдавать её кому угодно.

**AAD привязывает посылку к логину**: подставить чужой шифротекст под свой
`loginId` не выйдет.

**Логин нельзя занять поверх чужого.** Иначе любой зарегистрированный
пользователь угадал бы чужой логин и затёр строку, лишив человека способа
восстановиться.

**Ответы неразличимы.** Неверный пароль и несуществующий логин дают один и тот
же `recovery_not_found`: иначе сервер сам рассказывал бы, какие логины заняты.

### Честно о цене

- **Стойкость второго способа равна стойкости пароля.** Если база сервера
  утечёт, офлайн-перебор снова возможен: у атакующего будут и `verifier`, и
  `sealed`. Цена — 128 МиБ и три прохода Argon2id на попытку, то есть словарь из
  простых паролей вскроется. Поэтому короче 10 символов не принимается, а в
  интерфейсе способ подписан как менее надёжный, чем код.
- **Появляется связь «личность ↔ хеш логина»** — метаданная, которой раньше не
  было. Это осознанная плата за то, что человек не теряет аккаунт вместе с
  телефоном. Способ выключен по умолчанию и включается вручную.
- **Оба способа возвращают личность, но не переписку.** Старые сообщения
  защищены forward secrecy, ключи от них уничтожены вместе с устройством. Это не
  недоделка, это то, ради чего всё затевалось.
- **Код равен личности.** Кто им владеет — тот может добавить себе устройство от
  вашего имени. Контакты это заметят (код сверки сменится), но постфактум.

### Что делает сервер

Ничего сверх хранения непрозрачных байтов. Восстановление работает без единой
правки в пути входа: если личность серверу известна, а устройство новое, пропуск
не спрашивается — устройство регистрируется по одному сертификату, подписанному
восстановленным ключом.

## 6. Аутентификация

Challenge-response по Ed25519. Пароль на сервер не уходит никогда — его там просто нет.

```
1. C → S   открывает WSS
2. S → C   HELLO { nonce: 32 случайных байта, serverTime, heartbeatSec }
3. C → S   AUTH  { identity, device, deviceCert, sig, invite? }
4. S       проверяет:
             - nonce наш, не старше 30 с, не использован
             - deviceCert = sign(identity, "obsidian-device-v1"||identity||device)
             - sig        = sign(device,   "obsidian-auth-v1"  ||nonce||identity||device)
             - identity известен ИЛИ предъявлен валидный инвайт
5. S → C   AUTH_OK { deviceId, token, queued }
```

Доменные префиксы (`obsidian-auth-v1`, `obsidian-device-v1`) обязательны — без них подпись из одного контекста переиспользуется в другом.

Nonce одноразовый, хранится в памяти, TTL 30 секунд. `token` из AUTH_OK — Bearer для HTTP-эндпоинтов, живёт столько же, сколько WS-сессия.

Подпись проверяется против nonce **этого соединения**, а не против присланного клиентом: перехваченный AUTH на другом соединении не сойдётся. Каждый AUTH_ERR несёт свежий nonce, поэтому исправимую ошибку (занятый handle, протухший инвайт) клиент чинит повтором на том же сокете. Инвайт при этом не сгорает — он расходуется последним, уже после всех проверок.

## 7. Wire-протокол

Транспорт — WebSocket, **бинарные фреймы**. Base64 в JSON не используется нигде: +33% трафика и лишние аллокации на горячем пути.

```
байт 0    : opcode (u8)
байты 1.. : body
```

Целые числа — big-endian. Идентификаторы — 16 случайных байт. Служебные кадры несут JSON в body, кадры данных — сырые байты.

### Клиент → сервер

| Opcode | Имя | Body |
|---|---|---|
| `0x02` | AUTH | JSON `{v, identity, device, deviceCert, sig, invite?, paymentRef?, handle?}` |
| `0x05` | PAY_REQUEST | JSON `{v, identity, device, deviceCert, sig}` — выставить счёт в TON |
| `0x10` | SEND | `[16B clientRef][32B recipientDevicePub][4B ttlSec][ciphertext]` |
| `0x12` | ACK | `[16B envelopeId]` |
| `0x14` | KEYPKG_PUBLISH | `[[4B len][keyPackage]]...` — выложить свои MLS KeyPackages |
| `0x15` | KEYPKG_CLAIM | `[16B clientRef][32B devicePub]` — забрать один чужой |
| `0x1a` | RECOVERY_SET | JSON `{loginId, verifier, sealed}` либо `{clear:true}` — положить или снять посылку |
| `0x1b` | RECOVERY_GET | JSON `{loginId, token}` — **единственный кадр до AUTH** |
| `0x20` | PING | пусто |

### Сервер → клиент

| Opcode | Имя | Body |
|---|---|---|
| `0x01` | HELLO | JSON `{v, nonce, serverTime, heartbeatSec, maxFrame, entry}` |
| `0x03` | AUTH_OK | JSON `{deviceId, token, queued}` |
| `0x04` | AUTH_ERR | JSON `{code, message, nonce}` — новый challenge для повтора |
| `0x11` | ENVELOPE | `[16B envelopeId][8B serverTs][ciphertext]` |
| `0x13` | SEND_OK | `[16B clientRef][16B envelopeId]` |
| `0x16` | KEYPKG | `[16B clientRef][1B found][keyPackage]` — `found=0` значит «пакетов нет» |
| `0x1c` | RECOVERY_OK | пусто — посылка принята или снята |
| `0x1d` | RECOVERY_BLOB | JSON `{sealed}` — запечатанный identity-ключ |
| `0x21` | PONG | пусто |
| `0x30` | ERROR | JSON `{code, message}` |
| `0x31` | QUEUE_DONE | пусто — очередь отложенных доставлена |
| `0x06` | PAY_INFO | JSON `{ref, address, amountNano, expiresAt, paid, nonce}` |
| `0x07` | PAY_OK | JSON `{ref}` — счёт закрыт, можно слать AUTH |

### Правила

- **Heartbeat: PING каждые 30 с.** Cloudflare рвёт WebSocket после ~100 с без трафика — это не опция, а требование.
- Нет PING дольше 90 с → сервер закрывает соединение.
- Конверт удаляется из БД **только по ACK**. До этого он переживает падение сервера и переподключение клиента.
- Максимальный размер кадра — 1 MiB. Больше — через blob-эндпоинт.
- Неизвестный опкод или битая длина → close(1002), без попыток восстановления.
- **Порядок доставки задаёт `seq`, а не время.** Приглашение в группу обязано прийти раньше первого
  сообщения — иначе его нечем расшифровать, — а `created_at` в миллисекундах не различает кадры,
  отправленные подряд.
- **KeyPackages ходят по тому же сокету.** Отдельный HTTP-путь означал бы в ядре второй TLS-клиент и
  второй путь аутентификации ради двух запросов. Пакеты публикуются под устройством из сессии, а не из
  кадра, и выдаются ровно один раз: переиспользование KeyPackage ломает forward secrecy.
- **Padding.** Клиент добивает шифротекст до бакетов 256 / 1024 / 4096 / 16384 байт. Длина сообщения — это утечка, и закрывать её должен отправитель, а не сервер.

## 8. Схема БД сервера

**Решение по СУБД:** SQLite через встроенный `node:sqlite` (WAL). Причины: Postgres и Docker на хосте отсутствуют, нагрузка — десятки пользователей, а нулевые внешние зависимости прямо работают на цель по supply chain. Весь SQL изолирован в `src/db/` за узким репозиторием, переезд на Postgres — замена одного файла.

```sql
users        (identity BLOB PK, handle TEXT UNIQUE NULL, created_at INT)
payments     (ref TEXT PK, identity BLOB, amount_nano TEXT,
              created_at INT, expires_at INT, paid_at INT NULL)
chain_cursor (id INT PK, last_lt TEXT, last_hash BLOB, updated_at INT)
devices      (id BLOB PK, identity BLOB, device_pub BLOB UNIQUE, cert BLOB,
              created_at INT, last_seen INT)
key_packages (id BLOB PK, device_pub BLOB, data BLOB, created_at INT)
recoveries   (login_id BLOB PK, identity BLOB UNIQUE, verifier BLOB, sealed BLOB,
              updated_at INT)                        -- §5b, всё непрозрачно
envelopes    (seq INTEGER PK AUTOINCREMENT, id BLOB UNIQUE,
              recipient_device BLOB, payload BLOB, created_at INT, expires_at INT)
invites      (code_hash BLOB PK, created_at INT, expires_at INT)
blobs        (id BLOB PK, size INT, created_at INT, expires_at INT)
```

**Чего в схеме нет и не будет:**

- поля `sender` в `envelopes` — сервер не записывает, кто кому писал;
- поля `used_by` в `invites` — кто воспользовался кодом, не записывается: строка просто удаляется;
- контакт-листов и списков групп — они живут только на клиентах, зашифрованными;
- IP-адресов, User-Agent, истории входов;
- какого-либо plaintext сообщений, имён чатов, вложений;
- логина и пароля восстановления в открытом виде: в `recoveries` лежат только хеши и шифротекст.

Единственная метаданная, добавленная ради восстановления, — связь `identity ↔ хеш логина` в
`recoveries`. Она появляется, только если человек сам включил вход по паролю (§5b).

`AUTOINCREMENT` у `seq` не украшение: без него SQLite переиспользует номера, освободившиеся после ACK, и очередь перемешается.

`envelopes` — очередь, а не архив. Строка живёт до ACK либо до `expires_at` (по умолчанию 14 суток). Уборщик проходит раз в час и делает физический `DELETE`. Флагов `deleted` нет: «удалено» значит удалено.

## 9. Вложения

1. Клиент шифрует файл XChaCha20-Poly1305 со случайным ключом.
2. Режет на чанки по 16 MiB — **на free-плане Cloudflare лимит тела запроса 100 MB**.
3. `POST /v1/blobs` → сервер возвращает id, храня непрозрачные байты в `blobs/`.
4. Ключ и список id уходят получателю внутри MLS-сообщения.

Сервер не знает ни имени файла, ни типа, ни размера оригинала. TTL блоба — 30 суток.

## 10. Закрытый доступ

Три независимых слоя. Каждый режет свой класс трафика.

1. **Cloudflare Access + service token.** Незалогиненный запрос не доходит до домашнего сервера вообще. Это защита от сканеров и от 0-day в собственном коде.
2. **Инвайт** — одноразовый код, в БД только `SHA-256(code)`, TTL 7 суток. Открытой регистрации нет. Оплата в TON — второй способ, сейчас выключен (§10a).
3. **Challenge-response по ключу** на каждое соединение.

Rate limit на неаутентифицированном пути: 5 попыток AUTH с соединения, 20 в минуту с IP (счётчик в памяти, IP не пишется на диск).

## 10a. Платный вход через TON — выключен

> **Сейчас вход только по инвайтам.** Механизм ниже написан и покрыт тестами, но в сборку не
> входит: на сервере он включается непустым `OBSIDIAN_TON_ADDRESS`, в ядре — сборкой
> `cargo build --features ton`. По умолчанию `ton-lite-client` и `@ton/core` не загружаются
> вовсе (они в `optionalDependencies`), а команда `request_invoice` в ядре просто не существует.
> `HELLO.entry.ton` при этом приходит `false`, и клиент сразу знает, что предлагать.

Второй способ попасть внутрь, помимо инвайта. Сервер проверяет оплату сам, опрашивая блокчейн через ADNL: никакого платёжного шлюза, который решал бы за нас, кто заплатил.

```
1. C → S   PAY_REQUEST { identity, device, deviceCert, sig }   ← та же подпись, что в AUTH
2. S → C   PAY_INFO    { ref, address, amountNano, expiresAt, nonce }
3. Пользователь шлёт перевод на address, указав ref в комментарии
4. Наблюдатель видит входящую транзакцию, сверяет memo и сумму → paid_at
5. S → C   PAY_OK { ref }                                      ← если клиент ещё на связи
6. C → S   AUTH { ..., paymentRef: ref, handle }
```

**Счёт привязан к identity.** Memo лежит в блокчейне открыто, и без привязки любой наблюдатель погасил бы чужую оплату своим ключом. Поэтому PAY_REQUEST требует той же подписи, что и AUTH, а `paymentRef` принимается только от той личности, на которую счёт выписан.

**Строка счёта удаляется в момент регистрации.** Связка «кошелёк ↔ личность» существует ровно столько, сколько нужно для проверки, и не переживает вход.

### Честно о приватности

TON — публичный реестр. Оплата навсегда связывает кошелёк плательщика с фактом покупки доступа именно к этому серверу: адрес получателя, сумма и время видны всем. Сервер этой связи не хранит, но **блокчейн хранит**.

Кому это важно — платить с кошелька, не связанного с личностью, и не с биржевого счёта, прошедшего KYC. Инвайт в этом смысле строго приватнее, и он остаётся основным способом входа.

Опрос блокчейна тоже виден: лайтсервер знает, чей адрес мы спрашиваем. `OBSIDIAN_TON_CONFIG` стоит нацелить на собственный узел — тогда не видит никто.

### Параметры

- Цена задаётся в TON (`OBSIDIAN_TON_PRICE`), не в долларах: курсовой оракул — ещё одна внешняя зависимость и ещё один наблюдатель. Админ пересчитывает сам.
- Допуск на комиссии — 2% (`OBSIDIAN_TON_TOLERANCE_BP`), недоплата ниже порога не засчитывается.
- Счёт живёт час, деньги, пришедшие позже, автоматически не зачисляются.
- Первый запуск встаёт на текущую вершину счёта и историю не читает: публичные лайтсерверы неархивные, а старые оплаты нам не нужны.
- Приватный ключ кошелька серверу не нужен — он только читает.

## 11. Транспорт и Cloudflare

| Ограничение | Следствие |
|---|---|
| WS рвётся после ~100 с простоя | PING/PONG каждые 30 с, реконнект с экспоненциальным backoff |
| Тело запроса ≤ 100 MB | Чанки вложений по 16 MiB |
| TLS терминируется на CF | Всё содержимое зашифровано до туннеля |
| CF видит IP и тайминги | Принято в модели угроз; onion-транспорт — фаза 7 |

Логи сервера: только ошибки, без идентификаторов. `access log` выключен. Никаких IP на диск.

## 12. Пуш-уведомления

Пуш — прямой канал утечки «кто, кому, когда» в Google/Apple.

- Содержимое в пуше **никогда**. Только «есть новое», без счётчиков и имён.
- Android: **UnifiedPush + self-hosted ntfy**, FCM — фолбэк для тех, кто не хочет ставить дистрибьютор.
- Windows: пуш не нужен, приложение держит соединение.

## 13. Правила разработки

Нарушение любого пункта — баг уровня «блокер», а не «стилистика».

1. Сервер не логирует тела кадров, pubkey, handle и IP.
2. В БД сервера не появляется ни одного нового поля, раскрывающего связь отправитель↔получатель.
3. Никакой криптографии вне `obsidian-core`. UI-слой не шифрует и не хранит ключи.
4. Все внешние байты парсятся с проверкой длины **до** обращения по смещению.
5. Прямые npm-зависимости сервера — не больше 20. Установка с `--ignore-scripts`, только `npm ci`.
6. Сравнение секретов — только constant-time.
7. Ключи не попадают в логи, в бэкапы и в буфер обмена.

## 15. Чего ещё нет

Переписка шифруется, но продукта пока нет — нет ни одного интерфейса. Не сделано:

- **padding шифротекста** — описан выше в §7, но не реализован: длина сообщения пока утекает,
  и голосовые с фото делают её особенно говорящей;
- **привычка сверять.** Коды сверки и проверки состава есть в ядре и выведены в Windows-клиент
  (§5, §5a), но пока пользователь не сравнивает их по другому каналу, сервер способен на MITM при первом контакте — это единственная дыра,
  которую криптография сама не закрывает;
- **группы больше двух.** MLS их умеет, ядро — ещё нет: `start_conversation` заводит группу на двоих;
- **мультидевайс на приём.** Отправитель шифрует одному устройству; чтобы переписка появлялась на всех
  устройствах получателя, нужно шифровать каждому и склеивать беседы;
- **вложения** (blob-эндпоинты на сервере готовы, ядро их не использует);
- **sealed sender** — сервер по-прежнему знает, какому устройству доставить конверт;
- **пуш-уведомления, onion-транспорт, деплой за cloudflared.**
