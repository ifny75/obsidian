# Valanium mesh

Узлы соединены WireGuard-сетью `10.77.0.0/24`:

- `10.77.0.1` — main, приложение и данные;
- `10.77.0.2` — hop1;
- `10.77.0.3` — hop2.
- `10.77.0.4` — зарезервирован для hop3;
- `10.77.0.5` — hop4.

Публичные адреса узлов здесь намеренно не названы: этот файл лежит в открытом
репозитории, а список машин с открытым SSH — готовая карта для того, кто будет
искать, куда стучаться. Свои адреса держите в инвентаре развёртывания.

Main публикует nginx только на `10.77.0.1:8080`. Relay-узлы принимают
Cloudflare Tunnel на `127.0.0.1:8080`, Tor onion service на
`127.0.0.1:8082` и второй этап Multi-hop на WireGuard-порту `8081`.

Маршруты клиента:

- Basic: `wss://valanium.com/ws` — выбранный Cloudflare connector → main;
- Multi-hop: `wss://valanium.com/multihop/ws` — входной relay → второй relay → main;
- Onion: `valanium://onion` — ядро берёт адреса из HELLO, ходит через локальный
  SOCKS5 Tor/Orbot.

## Что какой маршрут прячет

**Raw-адрес клиента не доезжает до main ни в одном relay-маршруте.** На Basic
и Multi-hop его видят Cloudflare и ingress relay, после чего
`CF-Connecting-IP` заменяется на суточный blinded token. Дополнительный hop
не скрывает адрес от Cloudflare или ingress, но отделяет входной узел от main.
Onion исключает Cloudflare и доставляет на main только общую метку `onion`.

## Заголовок входа

`valanium-proxy.conf` выставляет `CF-Connecting-IP` и `X-Valanium-Route`
принудительно, по `$server_port`: `8082` — Tor, остальное — Cloudflare.
Прислать их клиенту нельзя, что бы он ни отправил.

Это не формальность. На onion-входе Cloudflare нет, перезаписать заголовок с
адресом там некому, и без этой подстановки клиент через Tor назначал бы себе
любой IP: обходил бы все лимиты и приписывал бы свой трафик чужому адресу.

Соединения из Tor адреса не имеют вовсе и считаются одним общим ведром
(`ONION_KEY`) со своими потолками — `VALANIUM_MAX_ONION_CONNECTIONS` и
`VALANIUM_ONION_LIMIT_FACTOR`. Ведро общее, поэтому потолки заметно щедрее; от
подбора пароля защищает не оно, а счётчик попыток на конкретный логин, который
считается независимо от входа.

## Адрес клиента

До main он больше не доезжает. На входном узле `CF-Connecting-IP` заменяется на
жетон — HMAC от подсети клиента и текущей даты (`valanium-blind.js`), — а сам
заголовок обнуляется. Второй узел и main видят только строку, из которой IP не
восстановить; приложение считает по ней лимиты, как считало по адресу.

Что нужно на узлах:

```bash
apt-get install libnginx-mod-http-js
openssl rand -hex 32 > /etc/nginx/valanium-blind.key
chown root:www-data /etc/nginx/valanium-blind.key && chmod 640 /etc/nginx/valanium-blind.key
```

Каждый ingress relay получает отдельный секрет. Downstream relay не должен
иметь возможность перебрать IPv4-кандидаты с тем же ключом и восстановить
адрес по жетону. Цена независимых ключей: один клиент получает разные жетоны
на разных Cloudflare-коннекторах, поэтому его rate-limit может разделиться
между узлами. Нужны дополнительные identity-wide и глобальные лимиты на main.

В сообщение подмешивается дата, поэтому жетон **меняется каждые сутки**.
Плата: в полночь адресные счётчики начинаются заново.

Обратной таблицы «жетон → адрес» нет и не будет: она превратила бы «мы не
знаем» в «мы знаем, но обещали не смотреть», и изъяли бы её первой.

Cloudflare адрес по-прежнему видит — от него прячет только Onion. Входной узел
видит его доли секунды в памяти и никуда не пишет.

## Onion-адреса

Все активные relay держат независимый скрытый сервис. Список отдаёт сервер в HELLO
(`VALANIUM_ONION_HOSTS` в `.env` на main), клиент его запоминает и обновляет
сам. В сборках остаются оба адреса как запасные — на случай первого запуска,
когда HELLO ещё не получали. Смена узла больше не требует новой сборки.

Публичный firewall main не должен разрешать `80`, `443`, `8080`, `8787` или
`3000`. На `8080` разрешены только активные relay-адреса
`10.77.0.2`, `10.77.0.3` и `10.77.0.5` по `wg0`.
