# Obsidian mesh

Три узла соединены WireGuard-сетью `10.77.0.0/24`:

- `10.77.0.1` — main (`2.27.205.8`), приложение и данные;
- `10.77.0.2` — hop1 (`2.27.205.9`);
- `10.77.0.3` — hop2 (`31.76.29.56`).

Main публикует nginx только на `10.77.0.1:8080`. Relay-узлы принимают
Cloudflare Tunnel на `127.0.0.1:8080`, Tor onion service на
`127.0.0.1:8082` и второй этап Multi-hop на WireGuard-порту `8081`.

Маршруты клиента:

- Basic: `wss://getobsidian.xyz/ws` — выбранный Cloudflare connector → main;
- Multi-hop: `wss://getobsidian.xyz/multihop/ws` — входной relay → второй relay → main;
- Onion: `obsidian://onion` — ядро берёт адреса из HELLO, ходит через локальный
  SOCKS5 Tor/Orbot.

## Что какой маршрут прячет

**Адрес клиента от main прячет только Onion.** На Basic и Multi-hop его ставит
Cloudflare в `CF-Connecting-IP`, и заголовок доезжает до main через все узлы:
лишний relay на пути этого не отменяет. Multi-hop нужен не для анонимности, а
для того, чтобы вход не зависел от одного узла. Так это и написано в обоих
клиентах — обещать большее нельзя.

## Заголовок входа

`obsidian-proxy.conf` выставляет `CF-Connecting-IP` и `X-Obsidian-Route`
принудительно, по `$server_port`: `8082` — Tor, остальное — Cloudflare.
Прислать их клиенту нельзя, что бы он ни отправил.

Это не формальность. На onion-входе Cloudflare нет, перезаписать заголовок с
адресом там некому, и без этой подстановки клиент через Tor назначал бы себе
любой IP: обходил бы все лимиты и приписывал бы свой трафик чужому адресу.

Соединения из Tor адреса не имеют вовсе и считаются одним общим ведром
(`ONION_KEY`) со своими потолками — `OBSIDIAN_MAX_ONION_CONNECTIONS` и
`OBSIDIAN_ONION_LIMIT_FACTOR`. Ведро общее, поэтому потолки заметно щедрее; от
подбора пароля защищает не оно, а счётчик попыток на конкретный логин, который
считается независимо от входа.

## Адрес клиента

До main он больше не доезжает. На входном узле `CF-Connecting-IP` заменяется на
жетон — HMAC от подсети клиента и текущей даты (`obsidian-blind.js`), — а сам
заголовок обнуляется. Второй узел и main видят только строку, из которой IP не
восстановить; приложение считает по ней лимиты, как считало по адресу.

Что нужно на узлах:

```bash
apt-get install libnginx-mod-http-js
openssl rand -hex 32 > /etc/nginx/obsidian-blind.key   # ОДИН И ТОТ ЖЕ на обоих
chown root:www-data /etc/nginx/obsidian-blind.key && chmod 640 /etc/nginx/obsidian-blind.key
```

**Секрет обязан совпадать на обоих relay**: иначе один человек получит разные
жетоны в зависимости от того, какой коннектор выбрал Cloudflare, и потолки
размажутся вдвое. В сообщение подмешивается дата, поэтому жетон **меняется
каждые сутки** — связать вчерашнюю активность с сегодняшней нельзя даже нам.
Плата: в полночь счётчики лимитов начинаются заново.

Обратной таблицы «жетон → адрес» нет и не будет: она превратила бы «мы не
знаем» в «мы знаем, но обещали не смотреть», и изъяли бы её первой.

Cloudflare адрес по-прежнему видит — от него прячет только Onion. Входной узел
видит его доли секунды в памяти и никуда не пишет.

## Onion-адреса

Оба relay держат свой скрытый сервис. Список отдаёт сервер в HELLO
(`OBSIDIAN_ONION_HOSTS` в `.env` на main), клиент его запоминает и обновляет
сам. В сборках остаются оба адреса как запасные — на случай первого запуска,
когда HELLO ещё не получали. Смена узла больше не требует новой сборки.

Публичный firewall main не должен разрешать `80`, `443`, `8080`, `8787` или
`3000`. На `8080` разрешены только `10.77.0.2` и `10.77.0.3` по `wg0`.
